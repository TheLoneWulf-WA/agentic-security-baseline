Review cost — why the reviews were capped, and how risk is decided

On 2026-11-10 the review loop got limits: a pass cap, a rule for wording-only findings, a cheaper model for Layer 0, a narrower three-role review, and cheaper reviewers for docs-only PRs. This page explains why, how “docs-only” is decided without judgment, the file classifier that was tried and dropped, and what still stands between a PR and the money and data it could touch.

Section 01

Why the reviews were capped

The loop was working. It was also costing more than the plan allowed.

The problem

Usage was hitting plan limits, and late passes found little

Review-until-clean has no natural stop: every fix earns a fresh pass, and every pass ran on the most capable model. On top of that, Layer 0 reviews every turn of every session. Across several sessions a day, usage was hitting plan limits.

Looking at what the passes actually found showed where the money went. The first one or two passes found the real problems. Later passes mostly found wording in the PR description: a sentence that no longer matched the code after a fix. Those are worth fixing, but they do not need a whole new round of reviewers to find, and fixing them does not change what the code does.

The aim

Spend the expensive review where a mistake is expensive, and stop paying full price to re-check prose. The limits below cut cost on low-risk PRs and late passes. None of them removes a review from a PR that touches money, access or customer data.

Section 02

What the limits are

The exact rules live in CLAUDE.md and the skills. This is the summary.

Summary

Six changes, one direction

LimitWhat it does
Pass cap3 loop passes, plus a 4th only for an open MEDIUM or HIGH code finding. Wording-only findings (PR body, comments, docs prose) are fixed in one batch and never start a pass by themselves; the final code review checks them. Still open after the 4th: the verdict is NOT CLEAN and the user is told.
ModelsThe bug reviewer is always Opus on any PR with code; compliance reviewers are always Sonnet. Only a PR of nothing but docs, images or styles gets two Sonnet reviewers. /adversarial-review is unchanged.
/code-review sizeA docs-, images- or styles-only PR of 150 changed lines or fewer gets 2 Sonnet agents instead of 4. Any other PR, or any PR where the script can’t run, gets all 4.
Layer 0 modelThe in-session security plugin is set to Sonnet 5.5 via SECURITY_REVIEW_MODEL / SG_AGENTIC_MODEL (the installer sets neither). It fires every turn, so its model sets a per-turn cost, not a per-PR one. It is an early net; the gates behind it decide.
Adversarial triggerThe three-role review still runs on auth, uploads, payments, input endpoints and anything an attacker can reach. For the admin it now runs on actions that move money or change accounts or permissions, not on admin wording, layout, help text or read-only display.
Light laneDocs-only and look-only PRs get one loop pass and the final code review. Anything touching payments, sign-in, sessions, customer data, the admin, uploads or a critical flow is never light lane, and neither is a PR the script calls sensitive.
Section 03

A mechanical test, not judgment

One of the limits depends on whether a PR is docs-only. Who decides that matters more than the limit itself.

The rule

A script decides, from the files the PR changes

~/.claude/scripts/pr-risk.sh <PR> prints RISK=normal only when every changed file, including the old name of a renamed one, is docs, images or styles by file type, and no added line contains a risky word. Anything else is RISK=sensitive. It also prints SIZE=small (150 changed lines or fewer) or large, and its reasons. /until-clean and /code-review run it and use what it says. A session may review a PR at higher risk than the script says, never lower.

Why not let the session decide

Models are probabilistic. Ask the session that wrote a PR whether its PR is docs-only, and the answer can vary from one run to the next. Worse, the session has a reason to prefer one answer: the cheaper review finishes sooner. A session judging its own PR can talk itself into the cheaper review: “this is basically a docs change”, when the same diff also touched a config file.

A file-type test doesn’t argue. The same PR gets the same answer every time, the reasons are printed, and anyone can check them.

Section 04

The classifier that was tried and dropped

The first design tried to sort every PR in every project into risky and not risky. It was cut back to the docs-only test above.

What was tried · 2026-11-10

A per-project file classifier

The first version used lists of risky paths, risky file names and risky words, shared across projects, plus a list for each project. Any PR that matched nothing got cheaper reviewers, including a cheaper bug reviewer. When that kept missing things, it was flipped to a safe list: each project listed the folders it considered safe, and everything else was sensitive.

Its own review took four passes and about twenty review agents. Each pass found more risky files the lists had missed, and one pass found a pattern bug that made a check fail open, passing what it should have flagged. All of it was fixed, but the pattern was clear: every new folder, framework and project needs the lists kept up, forever.

Why it was dropped

Classifying every file in every project is open-ended work, and the saving it bought was the smallest of the changes: a cheaper bug reviewer on code PRs that happened to be low risk. The real savings are elsewhere: the pass cap, the wording rule, Layer 0 on Sonnet and the narrower three-role review.

So the classifier was cut back to a test that needs no upkeep: is this PR only docs, images or styles? The bug reviewer stays on Opus for every PR with code. Where the old design would have guessed “low risk” about code, the new one doesn’t guess at all.

Section 05

Unknown means sensitive

Every way the script can fail ends in the normal, full review.

Fail closed

When the script can’t tell, the PR is sensitive

The script answers sensitive when:

  • any changed file is not docs, images or styles by type;
  • it can’t read the PR, its file list or its diff, or the PR lists no files;
  • a list is missing or empty, or a pattern in it doesn’t compile;
  • it fails in any other way, or Python can’t run it at all.

And /code-review runs its full set of four agents if the script can’t run.

Why

“Sensitive” here only means the review this protocol ran before the limits: an Opus bug reviewer and the full code review. A wrong “sensitive” costs some tokens. A wrong “normal” puts code in front of cheaper reviewers. So every doubt goes the cheap-to-be-wrong way.

Section 06

Two lists, the same for every project

No per-project lists, nothing to draft or keep up per repo.

The lists

~/.claude/risk-paths/

  • _default-safe.txtThe safe file types: pages and PDFs under docs/; Markdown and text files, but not dependency or build files (requirements and constraints files, CMakeLists.txt) and not the files that steer the agent and its reviews (CLAUDE.md, AGENTS.md, SKILL.md, anything under .claude/, commands/ or risk-paths/); licence and changelog files without an extension; images, video, audio, fonts, stylesheets, and .editorconfig, .gitattributes and data-only Prettier config. Matched by type, not folder, so code under a docs/ folder is still code.
  • _default-content.txtRisky words in the PR’s added lines. A match makes the PR sensitive even if every file is a safe type. See the next section.
Section 07

The content-word backstop

A file can be a safe type and still carry code.

Backstop

Risky words in what the PR adds

A Markdown page can hold a script tag, and an SVG can carry script. (MDX files run imports and JSX, so they are not on the safe list at all.) So the script also reads every line the PR adds (taken from the diff’s hunks, so an added line that itself starts with ++ still counts), and a match on any of these makes it sensitive:

  • third-party scripts and frames (<script, <iframe, next/script) and forms whose action is an outside URL;
  • database access, including Payload CMS’s Local API (getPayload, payload.find(), which skips access rules by default, service-role keys, row-level-security changes, DELETE FROM, DROP, TRUNCATE;
  • secret-shaped names (*_SECRET, *_API_KEY), cookie and CORS headers, redirect parameters, eval( and shell execution;
  • billing, in-app purchase and payment-provider names; keychain, keystore and crypto calls; webview bridges; exported Android components, cleartext and backup settings.

The words are matched case-sensitively and mostly as whole words, so DELETE FROM counts and a sentence saying “delete from the list” doesn’t. HTML tags are the exception: <SCRIPT counts as much as <script.

Section 08

What still protects money and data

The limits make the loop cheaper. They don’t touch the layers that guard the sensitive surfaces.

Unchanged

Five layers no limit reaches

  • The Opus bug reviewerEvery PR with code gets an Opus bug reviewer in every loop pass, and the full four-agent code review.
  • /security-reviewStill runs before the first push on any Strict Gate surface (payments, auth, secrets, input endpoints and the rest), and still blocks on HIGH.
  • The three-role review/adversarial-review still runs on auth, sessions, uploads, payments, admin actions that move money or change access, input endpoints, and scripts that run with access rules off or delete records. On those PRs it is the step that finds the most.
  • The code review/code-review --comment still runs on every PR, at the clean head. Only a docs-, images- or styles-only PR of 150 lines or fewer gets the smaller version.
  • The runtime testsThe local checks and the real run of the thing (a production build, real requests) come first in the review order, and a project’s tests for its critical flows still run. The light lane skips those flow tests only on PRs that are docs or styling outside those flows.
Where the savings come from

Late passes, wording-only fixes, Layer 0’s per-turn reviews, the three-role review no longer running on admin wording and layout, and cheaper reviewers on docs-only PRs. Code is reviewed as it was before.

Section 09

Known weaknesses

The test is small on purpose. These are its limits.

Honest limits

What this misses

  • The word list is only as good as its words. A docs or styles PR that adds something risky using no listed word (a stylesheet that loads from elsewhere, an SVG trick) comes out normal and gets Sonnet reviewers.
  • Content words only look at added lines. A docs PR that deletes a warning or a step from a runbook isn’t flagged; the reviewers still read it.
  • The lists in ~/.claude/ are not guarded. The config-edit gate asks before an agent edits hooks, skills, commands, settings or CLAUDE.md. It does not cover ~/.claude/scripts/ or ~/.claude/risk-paths/, so an agent could widen the safe list without a prompt.
  • Size is lines, not meaning. It only decides the code review’s agent count, and only on PRs already judged docs-only.
What to do about it

Be slow to add types to the safe list, and quick to add words to the content list. When in doubt about a PR, review it higher: the rule is never lower than the script, and higher is always allowed.
