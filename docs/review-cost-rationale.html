Review cost — why the reviews were capped, and how risk is decided

On 2026-11-10 the review loop got limits: a pass cap, cheaper models where the risk is low, a smaller code review for small low-risk PRs, and a cheaper model for Layer 0. This page explains why, how a PR’s risk is decided without per-PR judgment, and what still stands between a PR and the money and data it could touch.

Section 01

Why the reviews were capped

The loop was working. It was also costing more than the plan allowed.

The problem

Usage was hitting plan limits, and late passes found little

Review-until-clean has no natural stop: every fix earns a fresh pass, and every pass ran on the most capable model. On top of that, Layer 0 reviews every turn of every session. Across several sessions a day, usage was hitting plan limits.

Looking at what the passes actually found showed where the money went. The first one or two passes found the real problems. Later passes mostly found wording in the PR description: a sentence that no longer matched the code after a fix. Those are worth fixing, but they do not need a whole new round of reviewers to find, and fixing them does not change what the code does.

The aim

Spend the expensive review where a mistake is expensive, and stop paying full price to re-check prose. The limits below cut cost on low-risk PRs and late passes. None of them removes a review from a PR that touches money, access or customer data.

Section 02

What the limits are

The exact rules live in CLAUDE.md and the skills. This is the summary.

Summary

Six changes, one direction

LimitWhat it does
Pass cap3 loop passes, plus a 4th only for an open MEDIUM or HIGH code finding. Wording-only findings (PR body, comments, docs prose) are fixed in one batch and never start a pass by themselves; the final code review checks them. Still open after the 4th: the verdict is NOT CLEAN and the user is told.
Models by riskIn the /until-clean loop: on a sensitive PR the bug reviewer runs on Opus; everything else, and every compliance reviewer, runs on Sonnet. In /code-review: the Opus bug agents stay on every PR except small normal-risk ones. /adversarial-review is unchanged.
/code-review sizeA normal-risk PR of 150 changed lines or fewer gets 2 Sonnet agents instead of 4. Any other PR, or any PR where the risk script can’t run, gets all 4.
Layer 0 modelThe in-session security plugin is set to Sonnet 5.5 via SECURITY_REVIEW_MODEL / SG_AGENTIC_MODEL (the installer sets neither). It fires every turn, so its model sets a per-turn cost, not a per-PR one. It is an early net; the gates behind it decide.
Adversarial triggerThe three-role review still runs on auth, uploads, payments, input endpoints and anything an attacker can reach. For the admin it now runs on actions that move money or change accounts or permissions, not on admin wording, layout, help text or read-only display.
Light laneDocs-only and look-only PRs get one loop pass and the final code review. Anything touching payments, sign-in, sessions, customer data, the admin, uploads or a critical flow is never light lane.
Section 03

Risk from files, not judgment

Two of the limits depend on whether a PR is sensitive. Who decides that matters more than the limits themselves.

The rule

A script decides, from the files the PR changes

~/.claude/scripts/pr-risk.sh <PR> reads the PR’s changed files and added lines, checks them against safe and sensitive lists, and prints RISK=sensitive or RISK=normal, with SIZE=small or large and the reasons. /until-clean and /code-review run it and use what it says. A session may review a PR at higher risk than the script says, never lower.

Why not let the session decide

Models are probabilistic. Ask the session that wrote a PR whether its PR is sensitive, and the answer can vary from one run to the next. Worse, the session has a reason to prefer one answer: the cheaper review finishes sooner. A session judging its own PR can talk itself into the cheaper review: “this only touches the admin’s labels”, when the same diff also changed who can see the page.

A file list doesn’t argue. The same PR gets the same answer every time, the reasons are printed, and anyone can check them. The judgment goes into writing the list, once, in the open, where it can be reviewed. Not into each PR, under time pressure, by the author.

Section 04

From a risky list to a safe list

The first version listed what was risky. Reviewing that list showed why a list of risky things can’t be trusted to be complete.

The flip · 2026-11-10

Normal only when every file is known to be safe

The first version of pr-risk.sh called a PR sensitive when a file matched a risky list, and normal otherwise. Then the list itself was reviewed. Over four passes, each pass found risky files the list had missed: 18 in all. There was also a bug in a pattern that made a check fail open, so it passed what it should have flagged. All were fixed, but the lesson was plain: with a risky list, every file nobody thought of gets the cheap review.

So the logic is now the other way round. A PR is normal only when every changed file, including the old name of a renamed one, is on a safe list, and no sensitive signal fires. Everything else is sensitive.

Why missed files must fail safe

Both kinds of list will have gaps. The question is which way a gap fails. A gap in a risky list sends a risky file to the cheap review, which is the expensive mistake. A gap in a safe list sends a harmless file to the full review, which only costs tokens. Safe things are also easier to list: docs, images, fonts and styles look much the same in every project. Risky things don’t.

Section 05

Unknown means sensitive

A file nobody listed is sensitive, and so is anything the script can’t read.

Fail closed

When the script can’t tell, the PR is sensitive

The script answers sensitive when:

  • a changed file is on no safe list;
  • it isn’t inside a git repository, can’t read the PR, its file list or its diff, or the PR lists no files;
  • a shared list is missing or empty, or a pattern in any list doesn’t compile;
  • it fails in any other way, or Python can’t run it at all.

And /code-review runs its full set of four agents if the script can’t run.

Why a project with no safe list gets the full review

The shared safe list knows what is harmless everywhere. It can’t know which of a project’s own code folders are harmless, so until someone has looked and written them down, only PRs of docs, images, fonts and styles get the cheaper review. “Nobody has said this folder is safe” is not evidence that it is.

This also makes the cost of skipping the list visible: a project without one pays for the full review on nearly every PR, which is a reason to write it.

Section 06

Shared defaults plus project lists

Lists that ship with the baseline and cover common stacks, and lists per project that cover what only that project knows.

Shared defaults

~/.claude/risk-paths/_default-*.txt — web, Android, iOS, Expo

  • _default-safe.txtThe safe list for every project: pages and PDFs under docs/ (not code there), Markdown and text files, licence and changelog files, images, video, audio, fonts, stylesheets, editor config.
  • _default-paths.txtSensitive, and it overrides safe. For every project: .env files, CI and deploy config, dependency and lock files, infrastructure, scripts/, anything under .claude/, a root CLAUDE.md or AGENTS.md. Web: framework config, middleware, migrations and schema, SQL, API, server, webhook and action routes. Android: the manifest, network-security and backup rules, ProGuard, keystores, native code. iOS: Info.plist, entitlements, build config, the project file, app delegates. React Native and Expo: app.json, eas.json, native modules.
  • _default-names.txtSensitive names such as auth, session, admin, payment, checkout, upload, keychain, webview, deeplink. Applied to every file except docs (.md, .mdx, .txt, .rst, .adoc), so a guide titled “security” doesn’t count, but code under a docs/ folder does.
  • _default-content.txtSensitive words in the PR’s added lines. See the next section.
Project lists · new-project rule

<repo>/.claude/safe-paths.txt, drafted by --suggest

The first time a session works in a project with no safe list, it runs ~/.claude/scripts/pr-risk.sh --suggest. That prints folders, below the top level, where no file’s path or name trips a risky check. It doesn’t read file contents, so a drafted folder can still hold a risky call. The session reviews every line, and keeps only folders whose changes can’t touch money, sign-in, access, customer data, uploads, deletes, jobs, webhooks, config or third-party scripts. It opens the result as <repo>/.claude/safe-paths.txt in its own small PR, for the owner’s OK. When unsure, a line is deleted: an unlisted folder is only reviewed in full.

A project can also keep <repo>/.claude/risk-paths.txt, extra risky paths only it knows about, which override safe. Both project lists are read from the PR’s base branch (the local copy of origin/<base>).

Why the base branch, and why its own PR

A PR based on the default branch is judged by the lists as they were before it, so it can’t add its own files to the safe list or take them off the risky one. A PR that changes the lists is itself sensitive, because everything under .claude/ is on the shared risky paths. Keeping the list in its own small PR means that change gets reviewed on its own, at full strength.

Section 07

The content-word backstop

A folder can be on the safe list and still pick up a risky call. The script also reads what the PR adds.

Backstop

Risky calls in ordinary-looking files

In an Android or iOS app, a purchase, a keychain write or a webview bridge often sits in a screen file such as ProfileScreen.kt or SettingsView.swift. On the web, a safe-looking page can gain a third-party script or a form that posts elsewhere. So the script also reads every line the PR adds (taken from the diff’s hunks, so an added line that itself starts with ++ still counts), and a match on any of these makes it sensitive, whatever the safe lists say:

  • billing and in-app purchase APIs (BillingClient, StoreKit, RevenueCat) and payment providers by name;
  • keychain, keystore and crypto calls (SecItemAdd, KeyStore, CryptoKit, javax.crypto);
  • webview bridges (addJavascriptInterface, WKScriptMessageHandler, evaluateJavaScript);
  • exported Android components, cleartext traffic, backup and file-protection settings;
  • service-role keys, row-level-security policy changes, DELETE FROM, DROP, TRUNCATE;
  • secret-shaped names (*_SECRET, *_API_KEY), cookie and CORS headers, redirect parameters, eval( and shell execution;
  • third-party scripts and frames (<script, <iframe, next/script) and forms whose action is an outside URL;
  • direct database access from a page or component (Payload CMS’s Local API, such as getPayload and payload.find(, which skips access rules by default).

The words are matched case-sensitively and mostly as whole words, so DELETE FROM counts and a sentence saying “delete from the list” doesn’t.

Section 08

What still protects money and data

The limits make the loop cheaper. They don’t touch the layers that guard the sensitive surfaces.

Unchanged

Four layers no limit reaches

  • /security-reviewStill runs before the first push on any Strict Gate surface (payments, auth, secrets, input endpoints and the rest), and still blocks on HIGH.
  • The three-role review/adversarial-review still runs on auth, sessions, uploads, payments, admin actions that move money or change access, input endpoints, and scripts that run with access rules off or delete records. On those PRs it is the step that finds the most.
  • The code review/code-review --comment still runs on every PR, at the clean head. Only a normal-risk PR of 150 lines or fewer gets the smaller version.
  • The runtime testsThe local checks and the real run of the thing (a production build, real requests) come first in the review order, and a project’s tests for its critical flows still run. The light lane skips those flow tests only on PRs that are docs or styling outside those flows.
Where the savings come from

Low-risk PRs, late passes, and Layer 0’s per-turn reviews. A sensitive PR still gets an Opus bug reviewer in every pass, the full code review, and, on the surfaces above, the security review and the three-role review.

Section 09

Known weaknesses

A list is a trade: it removes judgment from each PR, and puts all of it into the lists.

Honest limits

What this misses

  • The lists are only as good as their paths. A risky folder wrongly put on a project’s safe list, changed without any listed name or word, comes out normal: Sonnet reviewers, and the smaller code review if the PR is small.
  • Folders drift. A folder that was harmless when it went on the safe list can later gain code that moves money or deletes data. Nothing flags that until someone takes the folder off the list, or adds it to the risky list. The rule says to do that when the new area appears; that step is a person’s, not the script’s.
  • Some “safe” files can carry code. SVG images can hold script, and a stylesheet can load from elsewhere. The word list catches <script in added lines, but not every trick.
  • A stacked PR is judged by its parent’s lists. When a PR’s base is another feature branch, the project lists come from that branch, which may carry an unreviewed change to them. And the base is read from the local origin/<base>, which can be out of date until the next fetch.
  • --suggest doesn’t read contents. It drafts folders from paths and names only, so every drafted line still needs a person’s review.
  • The lists in ~/.claude/ are not guarded. The config-edit gate asks before an agent edits hooks, skills, commands, settings or CLAUDE.md. It does not cover ~/.claude/scripts/ or ~/.claude/risk-paths/, so an agent could loosen the shared lists without a prompt.
  • Content words only look at added lines. A PR that only deletes a guard, in a folder on the safe list, isn’t caught by the word list.
  • Size is lines, not meaning. A one-line change can be the dangerous one. Size only decides the code review’s agent count, and only on PRs already judged normal.
What to do about it

Keep the project safe list short. Review it when the project changes shape. Take a folder off it the first time a review finds something risky there. When in doubt about a PR, review it higher: the rule is never lower than the script, and higher is always allowed.
