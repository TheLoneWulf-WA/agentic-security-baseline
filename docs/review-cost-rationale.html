Review cost — why the reviews were capped, and how risk is decided

On 2026-11-10 the review loop got limits: a pass cap, cheaper models where the risk is low, a smaller code review for small low-risk PRs, and a cheaper model for Layer 0. This page explains why, how a PR’s risk is decided without anyone’s judgment, and what still stands between a PR and the money and data it could touch.

Section 01

Why the reviews were capped

The loop was working. It was also costing more than the plan allowed.

The problem

Usage was hitting plan limits, and late passes found little

Review-until-clean has no natural stop: every fix earns a fresh pass, and every pass ran on the most capable model. On top of that, Layer 0 reviews every turn of every session. Across several sessions a day, usage was hitting plan limits.

Looking at what the passes actually found showed where the money went. The first one or two passes found the real problems. Later passes mostly found wording in the PR description: a sentence that no longer matched the code after a fix. Those are worth fixing, but they do not need a whole new round of reviewers to find, and fixing them does not change what the code does.

The aim

Spend the expensive review where a mistake is expensive, and stop paying full price to re-check prose. The limits below cut cost on low-risk PRs and late passes. None of them removes a review from a PR that touches money, access or customer data.

Section 02

What the limits are

The exact rules live in CLAUDE.md and the skills. This is the summary.

Summary

Six changes, one direction

LimitWhat it does
Pass capAt most 3 loop passes. Wording-only findings (PR body, comments, docs prose) are fixed in one batch and never start a pass by themselves; the final code review checks them. After pass 3, only a MEDIUM or HIGH code finding earns a 4th pass. Still open after that: the verdict is NOT CLEAN and the user is told.
Models by riskOn a sensitive PR the bug reviewer runs on Opus. Everything else, and every compliance reviewer, runs on Sonnet.
/code-review sizeA normal-risk PR of 150 changed lines or fewer gets 2 Sonnet agents instead of 4. Any other PR, or any PR where the risk script can’t run, gets all 4.
Layer 0 modelThe in-session security plugin runs on Sonnet 5.5. It fires every turn, so its model sets a per-turn cost, not a per-PR one. It is an early net; the gates behind it decide.
Adversarial triggerThe three-role review still runs on auth, uploads, payments, input endpoints and anything an attacker can reach. For the admin it now runs on actions that move money or change accounts or permissions, not on admin wording, layout, help text or read-only display.
Light laneDocs-only and look-only PRs get one loop pass and the final code review. Anything touching payments, sign-in, sessions, customer data, the admin, uploads or a critical flow is never light lane.
Section 03

Risk from files, not judgment

Two of the limits depend on whether a PR is sensitive. Who decides that matters more than the limits themselves.

The rule

A script decides, from the files the PR changes

~/.claude/scripts/pr-risk.sh <PR> reads the PR’s changed files and added lines, matches them against lists, and prints RISK=sensitive or RISK=normal, with SIZE=small or large and the reasons. /until-clean and /code-review run it and use what it says. A session may review a PR at higher risk than the script says, never lower.

Why not let the session decide

Models are probabilistic. Ask the session that wrote a PR whether its PR is sensitive, and the answer can vary from one run to the next. Worse, the session has a reason to prefer one answer: the cheaper review finishes sooner. A session judging its own PR can talk itself into the cheaper review: “this only touches the admin’s labels”, when the same diff also changed who can see the page.

A file list doesn’t argue. The same PR gets the same answer every time, the reasons are printed, and anyone can check them. The judgment goes into writing the list, once, in the open, where it can be reviewed. Not into each PR, under time pressure, by the author.

Section 04

Unknown means sensitive

Every way the script can fail to decide ends in the full review.

Fail closed

When the script can’t tell, the PR is sensitive

The script answers sensitive when:

  • it isn’t inside a git repository, can’t read the PR, or the PR lists no files;
  • a shared default list is missing;
  • the project has no list of its own yet.

And /code-review runs its full set of four agents if the script can’t run at all.

Why a project with no list gets the full review

The shared lists know common shapes: api/, migrations/, AndroidManifest.xml, a file named payment. They can’t know that in one project the money moves through a folder called ledger/, or that customer records are deleted from housekeeping/. Until someone has looked at the project and written those folders down, a “normal” answer would only mean “nothing matched a list that was never written for this project”. That is not evidence of low risk, so it isn’t treated as such.

This also makes the cost of skipping the list visible: a project without one pays for the full review on every PR, which is a reason to write it.

Section 05

Shared defaults plus a project list

Two layers of lists: one that ships with the baseline and covers common stacks, and one per project that covers what only that project knows.

Shared defaults

~/.claude/risk-paths/_default-*.txt — web, Android, iOS, Expo

  • _default-paths.txtFile paths, for every project: .env files, CI and deploy config, dependency and lock files, infrastructure, scripts/. Web: framework config, middleware, migrations and schema, SQL, API, server, webhook and action routes. Android: the manifest, network-security and backup rules, ProGuard, keystores, native code. iOS: Info.plist, entitlements, build config, the project file, app delegates. React Native and Expo: app.json, eas.json, native modules.
  • _default-names.txtFolder and file names such as auth, session, admin, payment, checkout, upload, keychain, webview, deeplink. Applied to code files only, so a guide titled “security” doesn’t count.
  • _default-content.txtWords in the PR’s added lines. See the next section.
Project list · new-project rule

<repo>/.claude/risk-paths.txt, drafted by --suggest

The first time a session works in a project with no list, it runs ~/.claude/scripts/pr-risk.sh --suggest. That prints a draft built from the project’s own folders that already match the shared lists. The session then reviews the draft: it removes false hits, and adds the project’s own money, access, customer-data, upload and delete areas that the shared lists can’t know. It opens the result as <repo>/.claude/risk-paths.txt in its own small PR, for the owner’s OK. Later, when a new risky area appears, its path is added to the list.

A list at ~/.claude/risk-paths/<repo-name>.txt also works, for a repo where you’d rather not commit one.

Why a draft, a review and its own PR

The draft saves the tedious part: it finds the folders the defaults already flag. The review adds the part only someone looking at this project can add. The separate PR keeps the list from riding along inside a feature PR, where the change that makes a PR cheaper to review would be reviewed at the cheaper level.

Section 06

The content-word backstop

Paths work well on the web, where risky code tends to live in risky folders. Mobile code is less tidy.

Backstop

Risky calls in ordinary-looking files

In an Android or iOS app, a purchase, a keychain write or a webview bridge often sits in a screen file such as ProfileScreen.kt or SettingsView.swift, which no path or name list would flag. So the script also reads the PR’s added lines, and a match on any of these makes it sensitive:

  • billing and in-app purchase APIs (BillingClient, StoreKit, RevenueCat) and payment providers by name;
  • keychain, keystore and crypto calls (SecItemAdd, KeyStore, CryptoKit, javax.crypto);
  • webview bridges (addJavascriptInterface, WKScriptMessageHandler, evaluateJavaScript);
  • exported Android components, cleartext traffic, backup and file-protection settings;
  • service-role keys, row-level-security policy changes, DELETE FROM, DROP, TRUNCATE;
  • secret-shaped names (*_SECRET, *_API_KEY), cookie and CORS headers, redirect parameters, eval( and shell execution.

The words are matched case-sensitively, so Stripe counts and a sentence about stripes doesn’t.

Section 07

What still protects money and data

The limits make the loop cheaper. They don’t touch the layers that guard the sensitive surfaces.

Unchanged

Four layers no limit reaches

  • /security-reviewStill runs before the first push on any Strict Gate surface (payments, auth, secrets, input endpoints and the rest), and still blocks on HIGH.
  • The three-role review/adversarial-review still runs on auth, sessions, uploads, payments, admin actions that move money or change access, input endpoints, and scripts that run with access rules off or delete records. On those PRs it is the step that finds the most.
  • The code review/code-review --comment still runs on every PR, at the clean head. Only a normal-risk PR of 150 lines or fewer gets the smaller version.
  • The runtime testsThe local checks and the real run of the thing (a production build, real requests) come first in the review order, and a project’s tests for its critical flows still run. The light lane skips those flow tests only on PRs that are docs or styling outside those flows.
Where the savings come from

Low-risk PRs, late passes, and Layer 0’s per-turn reviews. A sensitive PR still gets an Opus bug reviewer in every pass, the full code review, and, on the surfaces above, the security review and the three-role review.

Section 08

Known weaknesses

A list is a trade: it removes judgment from each PR, and puts all of it into the list.

Honest limits

What this misses

  • The list is only as good as its paths. A risky change in a file no list names, using no listed word, comes out normal: Sonnet reviewers, and the smaller code review if it’s small.
  • New folders are missed until added. When a project grows a new area that moves money or deletes data, nothing flags it until someone adds its path. The rule says to add it when it appears; that step is a person’s, not the script’s.
  • A PR can change its own project list. The script reads .claude/risk-paths.txt from the checkout, and that file matches no default path, so a PR that edits the list is judged by its own edited list. That is why list changes go in their own PR; reviewing a list change as normal risk is a known gap.
  • The lists in ~/.claude/ are not guarded. The config-edit gate asks before an agent edits hooks, skills, commands, settings or CLAUDE.md; it does not cover ~/.claude/scripts/ or ~/.claude/risk-paths/.
  • Content words only look at added lines. A PR that only deletes a guard, in a file no path list names, isn’t caught by the word list.
  • Size is lines, not meaning. A one-line change can be the dangerous one. Size only decides the code review’s agent count on PRs already judged normal.
What to do about it

Treat the project list as code: review it when the project changes shape, and add a path the first time a review finds something the list should have flagged. When in doubt about a PR, review it higher; the rule is never lower than the script, and higher is always allowed.
